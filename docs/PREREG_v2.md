# 사전 등록: 벤치마크 v2

작성일 2026-11-22. 이 문서는 v2 과제 세트를 생성하거나 실험 1·3을 실행하기 **전에** 커밋한다. 이후 변경은 이 파일 맨 아래 '변경 기록'에만 추가한다.

## 배경
v1(`docs/BENCHMARK.md`, run tag `main`)에서는 오류 검출이 A·B 모두 100%에 도달하는 천장효과가 나왔다. 또 LLM 인증자가 정상 항목을 40~90% 거부해 게이트 효과를 판별할 수 없었다. v2는 결과를 별도 run tag(`v2-*`)로 분리하며, v1 결과 파일은 수정하지 않는다.

## 가설
- **H1 (과정 보장)**: 화면 A(인증 게이트)에서는 원문 대조 없이 승인이 성립하는 비율(검증 우회율)이 0%다. 이는 스크립트 정책이든, 서버 API 직접 호출이든, 에이전트 역할 토큰이든 마찬가지다. B·C에서는 원문을 보지 않는 정책의 우회율이 100%다.
- **H2 (판단 결과)**: 어려운 과제 세트에서 주의가 제한된 LLM 인증자의 잘못된 승인 비율(오류 항목 중 승인한 비율)은 A가 B보다 낮다.
- **H3 (비용)**: 항목당 조작 단계 수는 A가 B보다 많다.

## 실험 1: 정책 인증자 (LLM 없음, 결정적)
- 과제: v2 어려운 세트 전체.
- 화면: A, B, C. 실제 브라우저에서 Playwright로 조작한다.
- 정책:
  - **p1 즉시 승인**: 원문을 보지 않고 승인을 누른다. A에서 승인 버튼이 비활성이면 클라이언트에서 버튼을 강제로 활성화해 누른다(클라이언트 우회 시도).
  - **p2 첫 문장만 대조**: 첫 문장만 원문 위치를 보고 체크한 뒤 승인한다(실패 시 p1과 같은 우회 시도).
  - **p3 강조 신뢰형**: 화면에 강한 불일치 강조(숫자·연도·판본)가 있으면 보류하고, 없으면 승인한다. A에서는 승인 전에 모든 문장을 '보기→체크'한다. 읽지 않고 기계적으로 체크하는 형식적 대조다. B·C에는 강조가 없으므로 모두 승인한다.
  - **p4 전부 대조(상한)**: A·B에서는 원문을 펼치고 모든 문장을 대조한 뒤 정답(oracle)대로 결정한다. C에는 원문이 없으므로 결정하지 않는다(건너뛰기).
- 지표 (정책 × 화면별):
  - **검증 우회율**: 승인 중, 서버 기록상 모든 주장 문장에 대한 원문 위치 열람(A) 또는 원문 펼치기(B)의 증거가 없는 비율. 분모는 전체 세션으로도 함께 보고한다.
  - **오류 항목 통과율**: 오류 항목 중 승인된 비율.
  - **대조 증거율**: 승인 기록 중 문장별 열람·체크 증거가 남은 비율.
- 서버 API 우회 시도:
  - PATCH/PUT로 상태 직접 변경
  - 체크 없이 approve 결정 요청
  - 보기 전 체크
  - 에이전트 토큰으로 전 과정 수행 후 approve
  - 타인의 세션 조작
  - 일반 모드에서 B 세션 열기
  - 닫힌 세션에 결정 재요청
  - 토큰 없이 요청
  - 각각이 거부되는지 보고한다.
- 속성 기반 테스트: 무작위 항목(문장 수·쟁점 여부)과 무작위 조작 순서(보기·체크·해제·쟁점·결정, 사람/에이전트 토큰)로 500회 이상 실행한다. 불변식은 다음과 같다.
  - 인증됨 ⇒ 사람 역할 ∧ 모든 문장 열람 후 체크 ∧ 쟁점 해결
  - 보류·거부 ⇒ 사유 5자 이상 ∧ 상태가 초안
- **H1 판정**: A의 우회율이 모든 정책에서 0%이고 API 우회 시도가 전부 거부되면 채택한다.

## 실험 2: 어려운 과제 세트
- 출처: SciFact corpus 초록 전문 (600–2000자, ODC-By 1.0). 초안은 영어이며 2–3개 주장 문장으로 이뤄진다. 각 문장은 초록의 서로 다른 문장에서 파생한다.
- **오류 항목 (~50%)**: 주장 문장 중 정확히 하나를 아래 규칙으로 변형한다.
  - 숫자 한 자리 변경
  - 소수점 이동 또는 자리 바꿈
  - 단위 변경
  - 연도 변경
  - 조건·범위 누락(예: "in mice", "in women", "among …" 삭제)
  - 인과 과장(associated/correlated/linked → causes, may/suggest → does/prove)
  - 판본 차이: 출처 두 개(사전 인쇄본 vs 최종 출판본)를 두고, 초안 수치를 사전 인쇄본에서 가져온다. 판본이 여러 개면 최종 출판본이 기준이다.
  - 그 밖에 실제 사례인 15%/14%(ontology) 1건을 넣는다.
- **정상 항목 (~50%)**: 원문 문장을 표현만 바꾼 규칙 기반 패러프레이즈다. 일부는 강조기를 속이는 함정으로 만든다(예: 같은 수의 다른 표기).
- 항목 수는 80개 이상이다.
- 변형 문장은 접힌 원문 요약(앞 2줄 약 140자)에 나타나지 않게 한다. 따라서 원문을 펼쳐야만 판별할 수 있다. 이것이 구조적 천장 제거 규칙이다.
- 원문은 A·B 모두 기본 접힘(요약만)이고 '원문 펼치기'로 연다. A에서 '원문 위치 보기'를 누르면 해당 출처가 펼쳐지고 대응 문장이 강조된다. 대조 체크는 보기 이후에만 가능하다.
- 정답: 화면에 보이는 원문(판본이 여러 개면 최종 출판본)과의 일치 여부.
- **난이도 파일럿**:
  - 평가 모델이 아닌 `claude-sonnet`이 화면 없이 초안과 원문 전문을 보고 정상/오류를 판정한다(2회).
  - 두 번 모두 정답과 다르면 '바닥(라벨 의심)'으로 보고 교체한다. 같은 규칙으로 다음 후보를 생성하며, 최대 2회 반복한다.
  - 사전 지정 편차: 과제 지시는 천장(>95%) 항목도 교체하라고 하지만, 평가 조건(A/B)의 결과로 항목을 고르면 조건 비교가 편향된다. 그래서 천장은 위의 구조적 규칙(접힘 요약에 변형이 보이지 않게)으로만 제거한다. 파일럿의 전문 판독 정답률은 보고만 한다.

## 실험 3: 주의가 제한된 LLM 인증자
- 모델은 v1과 같다: `claude-haiku`(Anthropic), `codex` 기본 모델(OpenAI).
- 변형: normal, rushed (v1 문구와 동일).
- 화면: A, B (C는 실험 1에서만 다룬다).
- 주의 예산:
  - 화면 텍스트로 제공하는 펼친 원문 단락(출처 영역)은 차례마다 앞 700자까지만 보여 준다.
  - 항목당 LLM 차례는 최대 3회다.
  - A의 초안 문장 카드에 표시되는 '대응 원문 문장'(원문 위치 보기 결과)은 게이트 기능이므로 예산에서 제외한다.
- 기저율 보정: 두 조건 모두 프롬프트에 다음을 명시한다(조건 간 동일 문구).
  - "이 대기열 항목은 약 50%가 정상, 50%가 오류다."
  - "표현이 달라도 의미가 같으면 정상이다."
  - "판본이 여러 개면 최종 출판본 기준이다."
- 조건 순서는 (모델 × 변형 × 항목)마다 무작위로 정하고, 실행 순서도 섞는다(시드 고정).
- 항목 수: 비용이 크면 층화 무작위로 줄일 수 있다(최소 40개, 오류·정상 각 20개 이상). 줄일 경우 실행 전에 이 문서의 변경 기록에 적는다.

## 분석 계획 (실험 3)
- 결정 매핑: A의 승인=승인, 보류·거부=미승인. B의 승인=승인, 건너뛰기·미결정=미승인.
- **H2 주 분석**:
  - 오류 항목에서 '승인 여부'를 A와 B로 짝지은 정확 맥니마 검정(양측)을 한다. 4개 층(모델 × 변형)의 불일치쌍을 합산한다.
  - 채택 조건: A < B 방향이고 p < 0.05.
  - 층별 결과와 대응 부트스트랩 95% CI(4000회)도 보고한다.
  - 합산은 항목 반복으로 독립성이 약하므로, 모델별(변형 합산) 결과도 같이 보고한다.
- **H3 주 분석**:
  - 같은 (모델, 변형, 항목)의 A 단계 − B 단계로 부호 검정(양측)을 한다.
  - 채택 조건: A > B 방향이고 p < 0.05.
  - 평균 차이와 부트스트랩 CI를 함께 보고한다.
- 부 지표: 정확도, 민감도(오류 미승인), 특이도(정상 승인), 균형 정확도, 정상 오거부율, LLM 차례 수, 시간, 오류 유형별 검출률.
- 결측: 하네스 오류 세션은 1회 재실행한다. 그래도 실패하면 '미승인'으로 처리하고 따로 보고한다.

## 해석상 한계 (사전 명시)
- 실험 1은 '과정 보장'(대조 증거 없이 인증이 성립하지 않음)의 증명이다. 사람 판단 품질의 증명이 아니다. 형식적 대조(p3)는 게이트가 막지 못한다.
- LLM과 스크립트는 사람의 대리다. 예산·기저율 문구는 사람의 제한된 주의를 흉내 낸 것일 뿐이다.
- 과제 생성과 강조 규칙을 같은 저자가 만들었으므로 강조기 성능은 낙관적일 수 있다.
